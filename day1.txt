# PilgrimAI — Day 1 Engineering Notes

## 0. Day 1 objective

The goal was **not** to build the actual temple/hotel/travel agents yet.

The goal was to build the **orchestration foundation** that can reliably take:

> User → understand request → resolve entities → build execution plan → handle dependencies → execute through LangGraph → preserve session state.

Final architecture:

```text
USER
  ↓
QUERY GATEWAY
  ↓
SAFETY + INTENT
  ↓
REDIS SESSION
  ↓
ONE LLM QUERY UNDERSTANDING
  ↓
ENTITY REGISTRY / DETERMINISTIC RESOLUTION
  ↓
QUERY PLANNER
  ↓
LANGGRAPH SUPERVISOR
  ↓
SPECIALIZED AGENTS
  ↓
EVIDENCE / TRUST
  ↓
DETERMINISTIC PLANNER
  ↓
VALIDATOR
  ↓
RESPONSE
```

Day 1 stopped at the **typed execution/orchestration layer**. Specialized agents are currently stubs.

---

# 1. Why we chose this architecture

The main design requirement was:

**Do not make the whole application one giant LLM prompt.**

An LLM is good at:

- understanding natural language
- identifying intent
- extracting entities
- understanding constraints
- understanding preferences
- decomposing complex requests
- understanding relationships between questions

But an LLM should **not** be trusted as the source of truth for:

- canonical entity IDs
- deterministic calculations
- dependency validation
- schedule arithmetic
- identity resolution
- final feasibility checks

Therefore we separated:

```text
SEMANTIC WORK
        ↓
LLM

DETERMINISTIC WORK
        ↓
Python / Registry / Planner / Graph
```

That separation is one of the most important architectural decisions in PilgrimAI.

# 13. Why only one understanding call

We explicitly rejected:

```text
LLM call 1 → understand
LLM call 2 → resolve entities
LLM call 3 → split queries
LLM call 4 → determine dependencies
```

That would cause:

- higher latency
- higher cost
- more failure points
- inconsistent interpretations
- unnecessary model dependence

Instead:

```text
ONE LLM
   ↓
structured QueryUnderstanding
   ↓
deterministic processing
```

# 15. Entity extraction

The LLM identifies an entity mention such as:

```text
Yadadri
Hotel Ashoka
that hotel
restaurant
```

But the LLM does **not** decide the canonical database ID.

For example:

```text
Yadadri
```

may later resolve to:

```text
T0001
```

That mapping is deterministic.

---

# 16. Entity types

Entities carry types.

Examples:

```text
temple
accommodation
restaurant
location
place
```

This matters because:

```text
Hotel Ashoka
```

should not be resolved against a temple registry entry.

---

# 17. Constraints

We introduced:

```text
QueryConstraint
```

with:

```text
name
value
constraint_type
hard
```

This separates:

```text
MUST HAVE
```

from softer preferences.

Example:

```text
must be near temple
```

can be a hard constraint.

---

# 18. Preferences

Preferences are separate from constraints.

Example:

```text
prefer vegetarian food
prefer budget hotel
prefer morning travel
```

Why?

Because:

```text
constraint != preference
```

A hard constraint can invalidate a plan.

A preference normally changes ranking or selection.

---

# 19. Dates and times

We capture semantic date/time expressions:

```text

tomorrow morning
```

The LLM identifies the semantic expression.

We deliberately did **not** build ad-hoc date arithmetic into Day 1.

Later orchestration will normalize relative dates using a proper calendar/date mechanism.

# 23. Multi-query decomposition

This was one of the most important Day 1 features.

A request such as:

```text
Find a hotel near Yadadri and then find a restaurant near that hotel.
```

is not one atomic task.

It becomes:

```text
q1 → find hotel near Yadadri

q2 → find restaurant near q1
```

---

# 24. Why decomposition matters

Without decomposition, the system might try to execute everything simultaneously.

But:

```text
restaurant near hotel
```

cannot be correctly executed until:

```text
hotel
```

is known.

Therefore we represent the relationship explicitly.

---

# 25. Dependencies

Every subquery can contain:

```text
dependencies
```

Example:

```json
{
  "query_id": "q2",
  "dependencies": ["q1"]
}
```

Meaning:

```text
q2 cannot execute until q1 has completed.
```

# 44. Session-aware plans

A major Day 1 requirement was:

```text

```

Therefore Redis stores the execution plan and step results.

```text

```

# 45. Session reference resolution

We initially tried phrase-based references such as:

```text
"that hotel" → q1
```

That failed because the LLM could rewrite the mention as:

```text
"hotel near Yadadri"
```

Therefore we changed the architecture.

---

# 46. Dependency-driven references

Now reference resolution uses:

```text
subquery dependencies
+
previous session steps
+
entity/domain compatibility
```

So:

```text
q2 depends_on q1
q1 domain = accommodation
q2 entity_type = accommodation
```

means:

```text
q2 entity
→ reference to q1
```

regardless of whether the LLM writes:

```text
that hotel
```

or:

```text
hotel near Yadadri
```

This is much more robust than a growing phrase dictionary.

---

# 47. `RESOLVED_REFERENCE`

We introduced:

```text
RESOLVED_REFERENCE
```

with:

```text
reference_step_id
```

Example:

```text
status = RESOLVED_REFERENCE
reference_step_id = q1
```

This is different from normal entity resolution.

We don't yet have the actual hotel canonical ID because the hotel agent hasn't returned one.

So:

```text
canonical_id = null
reference_step_id = q1
```

is correct at this stage.

---

# 48. The major planner bug we found

We encountered a subtle dependency bug.

Current-turn plan:

```text
q2 depends_on q1
```

but q1 belonged to the previous session turn.

If dependency validation happened **before merging session steps**, the planner saw:

```text
current plan:
q2
```

and concluded:

```text
q1 doesn't exist
→ BLOCKED
```

That was incorrect.

---

# 49. Correct dependency validation order

We fixed the architecture to:

```text
Current understanding
        ↓
Current resolution
        ↓
Current execution plan
        ↓
MERGE WITH SESSION PLAN
        ↓
COMPLETE PLAN
        ↓
VALIDATE DEPENDENCIES
        ↓
LANGGRAPH
```

This is the correct order.

## Day 1 design rules to preserve

1. **One LLM understanding call per user turn.**
2. **LLM does not assign canonical IDs.**
3. **Entity resolution is deterministic.**
4. **Ambiguity must not be guessed.**
5. **Unresolved entities can block execution.**
6. **Dependencies are explicit.**
7. **Session state lives in Redis, not the source-of-truth registry.**
8. **Current and previous execution plans must be merged before dependency validation.**
9. **LangGraph controls execution flow, not semantic understanding.**
10. **Agents should return structured results.**
11. **External evidence/provenance will be added to agent outputs.**
12. **Deterministic planning/validation remains outside the LLM.**
13. **Relative dates are understood first and normalized later.**
14. **Real agents come after orchestration is stable.**
15. **Do not solve every problem with another LLM call.**

### What we have now

The Day 1 deliverable is therefore **not merely a FastAPI demo**.

It is a working:

> **session-aware, multi-query, dependency-aware execution orchestration foundation**

with the real agent implementations intentionally deferred to Day 2.
